Problema

O time desenvolveu uma solução de allow-list estática com lookup in-memory. A liderança técnica questionou os números medidos localmente:

"Sem overhead de rede o ambiente local não representa o comportamento em produção. Os números estão inflados."
Resposta Medir com overhead de rede real via Docker bridge, mantendo o benchmark local para que o delta introduzido pela rede seja visível e mensurável.

Por que o mesmo padrão nos dois testes? Se o benchmark usasse 100% hits e o k6 usasse 70/30, a diferença de latência misturaria rede e padrão de acesso. Com 70/30 em ambos, o delta isola exclusivamente o overhead de rede.
Benchmark CPU Queries geradas em memória — 1M warmup + 5M medidas. 70% chamam PVs 1–1M (hits), 30% chamam PVs 1M+1–2M (misses).
k6 + Docker VUs escolhem aleatoriamente hits (1–500k) ou misses (1M+1–1.5M) com a mesma proporção 70/30 a cada iteração.

O que são p50, p95 e p99?

Percentis de latência descrevem a distribuição dos tempos de resposta de todas as requisições.

p50 p95 p99

← mais rápidas                                                               mais lentas →

p50 — Mediana

50% das requisições responderam abaixo deste valor. É a latência típica — o que a maioria dos usuários experimenta.

p95

95% das requisições responderam abaixo deste valor. Só 1 em cada 20 demorou mais. Representa o usuário com experiência ruim mas não excepcional.

p99 — SLA

99% das requisições responderam abaixo deste valor. Só 1 em cada 100 demorou mais. É o threshold de SLA porque cobre quase todos os casos reais.

Por que não usar a média? Se 99 requisições demoram 1ms e 1 demora 1.000ms, a média é ~11ms — não representa nem o caso típico nem o pior caso. Percentis revelam a distribuição real.

Prós e Contras

✓ Prós
  • Latência sub-milissegundo no algoritmo
  • Zero dependências externas em runtime
  • Scale-out horizontal trivial
  • Operação simples: deploy = atualização
  • Menor surface de falha operacional
  • Memória eficiente com primitivos fastutil
✗ Contras
  • Atualização requer redeploy (~15–30 min)
  • Startup lento com listas grandes
  • Sem visibilidade das listas em runtime
  • Mudanças frequentes tornam o redeploy custoso
Cenário ideal Listas estáveis com atualizações pouco frequentes (dias a semanas). Não usar se listas mudam diariamente.
